ROOT CAUSE: community.ibm.com is a JavaScript-rendered Single Page Application.
The article content is hydrated client-side — it does not exist in the static
HTML returned by an HTTP GET request. The extractor received only the page
skeleton and the IBM Community sidebar tagline ("IBM Guardium" topic group). This
is not an extractor bug introduced or regressed in 2.2.1; it is a fundamental
JS-rendering limitation of the current static fetch approach.

EVIDENCE: The 31 words extracted ("Join this online topic group to communicate
across Security product users…") are from the IBM Community topic group sidebar,
not the blog article. The article title IS extracted correctly from the <title>
tag, confirming the HTTP connection succeeded and the page loaded at all.

PROPOSED FIX (not released — awaiting user approval):
  Option A — Playwright / headless browser fetch: Add an optional
             `--headless` flag to ingest.py that uses playwright to render
             the page before scraping. Requires: pip install playwright + 
             playwright install chromium. Would resolve JS-rendered pages
             universally.
  Option B — Accept a saved HTML or Markdown export: User exports the blog
             post as HTML/Markdown locally and passes it to ingest.py as a
             --type txt or --type docx input. No new dependency, but manual
             step for the user.
  Option C — IBM Community RSS/API: If the community exposes a public API
             or RSS feed for blog posts, ingest.py could use that endpoint
             instead of HTML scraping.

The saved copy (blog_source.md) in narratives/guardium-exposure-qradar-test/
remains the best available source for narrative generation until one of the
above options is implemented.
